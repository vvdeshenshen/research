0.1 一个字形从文件到像素要经过什么

字体文件 (TTF/OTF/CFF/WOFF2)

01数据与坐标：光栅化的输入

1.1 缩放公式与定点数

  • 字体单位 FUnit 范围 −16384 到 16383；unitsPerEm 推荐为 2 的幂（TrueType 常用 2048，CFF 常用 1000）。
  • ppem = pointSize × dpi / 72；像素坐标 = FUnit × ppem / unitsPerEm。规范例子：2048 upem、18 磅、72 dpi 下 550 FUnit = 4.83 像素。
  • 像素坐标保留到 1/64 像素，即 F26Dot6（26 位整数 + 6 位小数）。控制值表 CVT 在指令中读出的永远是 26.6 像素；WCVTF 以 FUnit 写入，WCVTP 以像素写入。
  • FreeType 的平滑光栅器内部再上采样 4 倍：PIXEL_BITS = 8，ONE_PIXEL = 256。

1.3 缓存键：为什么一个字形会被光栅化很多次

Skia 的 SkScalerContextRec 决定一个"strike"（一套光栅化参数）：字体、字号、2×2 变换矩阵、标志（亚像素定位、LCD 垂直、BGR、由 LCD 生成 A8、hinting 等级、加粗）、掩码格式（BW/A8/LCD16/ARGB）、对比度、设备伽马、以及文字颜色的亮度位（用于预混伽马）。加上 SkPackedGlyphID = 字形 ID + 2 位 X 亚像素偏移 + 2 位 Y 亚像素偏移。所以同一个字形在不同颜色、不同 1/4 像素偏移、不同变量字体轴值下都是不同的缓存项。这是理解后面所有"缓存爆炸"讨论的基础。

03算法详解 I：hinting（网格对齐）

3.1 为什么需要 hinting

ppem 小于约 20 时，一条 1.3 像素宽的字干可能落成 1 像素或 2 像素，甚至两条边落在同一像素内而消失。TrueType 规范用 9 磅 Arial 的 "m" 举例：字干与像素网格的相位是"偶然效应"。grid fitting 的目标：字干粗细一致、灰度密度均匀、间距一致、不丢点，并让屏幕字体在 9 ppem 仍可读。

3.2 TrueType 指令虚拟机

三个程序：fpgm（字体程序，运行一次，用 FDEF/IDEF 定义函数与自定义操作码）、prep（CVT 程序，ppem 或变换改变时运行，初始化控制值表与图形状态）、每个字形自带的指令。每个程序开始时栈清空；图形状态在每个字形前重置（"字形之间没有记忆"）。maxp 表声明 VM 规模：maxZones、maxTwilightPoints、maxStorage、maxFunctionDefs、maxStackElements 等。

字干统一的机制：字干的第二条边用 MIRP[…R…] 引用一个 CVT 字干宽度项（例如 cvt 12 = 157 FUnit "x 字干粗细"）。当缩放后的 CVT 值与轮廓距离之差在 cut-in（17/16 像素）内，取整后的 CVT 值胜出，于是整个字体的所有字干得到同一个整数像素宽；minimum_distance（1 像素）防止字干消失；single_width_cut_in 在极小尺寸把所有受控宽度收敛到一个值。规范例子：cut-in 17/16 让 J 的底部曲线一直贴着基线到 81 ppem，82 ppem 起回到轮廓位置。

幻影点（光栅器 ≥ 1.7）：每个字形末尾附加 4 个点（左侧承、前进宽度、上原点、前进高度）。指令移动它们会改变"设备相关"的前进宽度，这就是 hinting 能改变字距的原因。hdmx 表按 ppem 缓存 uint8 前进宽度让布局不必跑光栅器；LTSH 记录每个字形从哪个 ppem 起宽度线性缩放（判据：ppem ≥ 50 且取整线性宽与取整 hint 宽之差 ≤ 2%）。

gasp 表：按 ppem 区间指定行为，位 0x0001 GRIDFIT、0x0002 DOGRAY、0x0004 SYMMETRIC_GRIDFIT、0x0008 SYMMETRIC_SMOOTHING；典型：< 9 ppem 只灰度不对齐，9–16 只对齐不灰度，> 16 两者都开，> 15 ppem 对称平滑。

3.3 ClearType 时代的"向后兼容"与 FreeType 的 v35/v38/v40

ClearType 让 hinting 网格在 x 方向变成 16 个子采样（"TrueType 的实际水平分辨率是 y 方向的十六倍"），y 方向仍是 1。为了让为二值渲染编写的旧 hint 不破坏 ClearType 输出，微软光栅器进入"向后兼容模式"：取整指令（RTG、RTHG、MDAP[R]、MIAP[R]、MDRP[R]、ROUND）取整到 1/16 网格；SCVTCI 的 cut-in 缩到 1/16，SMD 最小距离缩到 1/2；所有 DELTAP 跳过（除非作用于非 ClearType 方向已触碰的点）；并识别 TypeMan Talk 的特定函数签名（DStroke/IStroke 函数 64–66、间距函数 0/1/2/4/7/8、VacuFormRound、对角线函数 58）直接禁用。字体用 INSTCTRL 选择器 3 声明"原生 ClearType"可关闭这些 hack。

Adobe/FreeType CFF 引擎的算法（psblues.c、pshints.c，2013 年由 Adobe 的 Dave Arnold 捐赠）：

  1. cf2_blues_init：若 scale < blueScale 则 suppressOvershoot = TRUE，并加一个 boost = 0.6 − 0.6 × scale / blueScale（上限 0.5 像素，加深时禁用）后取整平边；BlueScale 被钳制使任何区不超过 1 像素。
  2. cf2_blues_capture：字干边落在 [底 − fuzz, 顶 + fuzz] 内即被捕获；压制时吸附到平边；否则若 csTop − csCoord ≥ blueShift 则至少离平边 1 像素；否则取整到最近像素。两条边同移同量并锁定。
  3. cf2_hintmap_build：优先级 = 合成 em 框 hint（CJK）→ 被蓝区捕获的锁定 hint → hintmask 中其余 hint；重叠/相触的丢弃。
  4. cf2_hintmap_adjustHints：第一遍自下而上把每条边吸附到像素边界，同时尊重前一条边与 CF2_MIN_COUNTER（反白最小值，合成边旁豁免）；第二遍自上而下重试。
  5. cf2_hintmap_map：字符空间坐标在相邻 hint 边之间线性插值（外部均匀缩放）。只做 y 方向，x 不动，这正是"light"模型。

词干加深（cf2_computeDarkening，"仿 Adobe Avalon 光栅器的 5 段曲线"）：x = 字干宽 × ppem（千分之一像素），y = 加深量（千分之一像素），默认断点 (500,400)、(1000,275)、(1667,275)、(2333,0)：字干 ≤ 0.5 像素加深 0.4 像素，1–1.667 像素加深 0.275，≥ 2.333 不加深，之间线性；结果每侧减半后换回字体单位。x 用 StdVW（缺省 75/1000 em），y 用 StdHW。FreeType 2.6.2 起对 cff/type1/autofit 默认关闭，因为它需要线性空间混合与伽马校正，否则"字形显得又重又糊"。

3.5 FreeType 自动 hinter（aflatin.c / afhints.c）

  1. 蓝区：从参考字符串取垂直极值：大写顶 THEZOCQS、大写底 HEZLOCUS、小写 f 顶 fijkdbh、x 高度顶 uvxzoesc、小写底 nrxzoesc、下延 pqgjy。每个字形的极值按 on 点跨度 ≥ upem/14 判为平边否则圆边；ref = 平边中位数，shoot = 圆边中位数。区在缩放后高度 < 3/4 像素时"激活"，压制过冲（相当于 BlueScale）。
  2. 标准宽度：hint 字形 o，收集相连字干宽度，按 upem/100 阈值排序量化，widths[0] 为标准宽。
  3. 线段：沿轮廓走，出方向等于主轴方向的连续点构成一段（AF_DIR_UP/DOWN/LEFT/RIGHT），记录 pos、delta、height、端点为控制点时标 ROUND。
  4. 连接：方向相反且重叠 ≥ 常量的段配对，评分 dist_demerit + 6000/overlap，dist_demerit = delta²/3000，互为最佳 = 字干，单向 = 衬线。
  5. 边：把 edge_distance_threshold（≤ 1/4 像素）内的段聚成边，跳过短于 1 像素或宽于 1/2 像素的段；边与蓝区在 max(upem/40 × scale, 1/2 像素) 内即吸附，圆边偏好 shoot。
  6. hint 边：(a) 先对齐蓝区边作锚；(b) 相连字干 stem.pos = base.pos + compute_stem_width(dist)，≤ 1.5 像素的字干用居中取整"巫术"（偏移 32），不会把字干压到 1/4 像素以下；小写 m 对称修正；(c) 衬线随基边移动，最小 1/2 像素；(d) 其余边在已 hint 的邻居间插值。
  7. compute_stem_width：light 分支不吸附该轴：衬线 < 3 像素不动；圆字干 < 80 单位 → 64；< 56 → 56；与 widths[0] 相差 < 40 单位则用标准宽（最小 48）；< 3 像素时小数部分量化（δ<10 保留，<32 加 10，<54 加 54）；≥ 3 像素按 ppem 相关的双取整修正。强分支：垂直永远取整到整数像素（(dist+16)&~63，最小 64），水平抗锯齿时 < 48 取 (dist+64)>>1，48–128 只在失真 < 1/4 像素时取整"以防 LCD 彩边"。
  8. 点对齐：align_edge_points 把段上所有点吸到边位置并标 TOUCH；align_strong_points（拐角/拐点）在边之间插值；align_weak_points = IUP：范围外平移、范围内 u = u1 + (u−v1)(u2−u1)/(v2−v1)。
  9. 模式：FT_LOAD_TARGET_NORMAL 两轴吸附；LIGHT "只在 y 轴吸附，如 FreeType 的 CFF 引擎或微软 ClearType"（2.7 起优先用驱动的原生垂直 hinting）；MONO 强 + 二值；LCD/LCD_V。fontconfig：hintnone/hintslight/hintmedium/hintfull，lcdfilter none/default/light/legacy，rgba rgb/bgr/vrgb/vbgr/none。

4.1 单色扫描转换与丢点控制

TrueType 规范的规则：

4.2 精确面积覆盖：FreeType 平滑光栅器

ftgrays.c（David Turner，2000，"基于 Raph Levien 的 libart"）：单遍、无中间位图、无排序、整数运算。

  • 每个被线段穿过的像素单元记录 {x, cover, area}，按扫描线链表存放。
  • 对单元内的每一小段：cover += Δy，area += Δy × (fx1 + fx2)，其中 fx1、fx2 是段两端在单元内的 x 位置，所以 area 是有符号梯形面积的两倍。
  • 扫描：单元的覆盖 coverage = area >> 9（即 >> (2 × PIXEL_BITS + 1 − 8)）；单元右侧直到下一单元的整段覆盖 = cover × 2 × ONE_PIXEL − cell.area 折算。
  • 填充规则：fill = 0x100（奇偶）或 INT_MIN（非零）；if (coverage & fill) coverage = ~coverage；非零时 coverage > 255 钳到 255。奇偶规则在 256 处折返，非零规则钳位。输出 256 级灰度。
  • 二次曲线展平：偏差 dx = max(|x0 + x2 − 2x1|, |y0 + y2 − 2y1|)，while (dx > ONE_PIXEL/4) { dx >>= 2; 分段数 <<= 1; }，每次二分把偏差降 4 倍。三次曲线在 |2P0 − 3P1 + P3| 或 |P0 − 3P2 + 2P3| 超过 ONE_PIXEL/2 时继续分割。

4.3 同一思想的三次演化：font-rs、Skia AAA、Vello Sparse Strips

font-rs（Raph Levien，2016）：把"扫描线顺序上有符号面积的有限差分"直接写进稠密累加缓冲，最后一遍做累积和、取绝对值、钳位、×255。窄情形（线段落在一个像素列内）：xmf = 0.5 × (x + xnext) − x0floor，a[x0] += d − d × xmf，a[x0+1] += d × xmf（d = Δy × 方向）；宽情形：a0 = 0.5 × s × (1 − x0f)²，am = 0.5 × s × x1f²。宣称比 FreeType 2.6.5 在 42 ppem 快 7.6 倍、12 ppem 快 4 倍。

Skia 解析抗锯齿（SkScan_AAAPath.cpp，2016）：不再用 16× 超采样的等距扫描线，只在整数 y、路径端点 y 和边交点处放扫描线，把路径分解为梯形并解析算覆盖；一个高 H 的三角形只需约 3+H 条扫描线而非 4H。

Vello Sparse Strips（2025–26，vello_common）：路径展平后按 4×4 像素瓦片分箱，每条线段对穿过的每个瓦片生成一条记录 {y, x, line_idx:27 | mask:5}（mask 位 = 上/下/左/右/环绕）并排序；条带（strip）是 4 像素高的水平行程 {x, y, alpha_idx | fill_gap}，只有边界瓦片携带每列 4 字节的 alpha，完全覆盖的行程用 fill_gap 标记为纯色填充。覆盖计算是"从左向右射线，像素的覆盖率是环绕数的积分"：每条线在像素内的 Δy 加给右侧所有像素，线段右侧在像素内的梯形加给该像素，用 f32x4 SIMD 一次算 4 条扫描线。非零：alpha = min(255, |w| × 255 + 0.5)；奇偶：|w − 2 × floor(w/2 + 0.5)|。CPU 版多线程合成条带，GPU 版把条带与 alpha 上传后用普通顶点/片段着色器光栅化，可跑 WebGL2。

4.4 伽马与对比修正

问题：over 合成在光强上是线性的。若在 sRGB 编码值上直接做，50% 覆盖得到编码值 0.5，对应约 21% 线性亮度。深字浅底时中间覆盖像素过暗，字显得更粗更重；浅字深底时字显得更细。FreeType 文档反过来说：正确的线性混合会把灰阶推向更亮，字"显得细"，于是需要词干加深；而"不做线性混合与伽马校正时，字形显得又重又糊"。Behdad Esfahbod 2024 年的综述指出 Linux 缺少线性混合是其文字观感不如 Windows/macOS 的原因。

Skia 的"伪伽马"（SkMaskGamma）：头注说明"普通掩码存线性 alpha；伽马校正掩码存非线性 alpha，试图在一个伽马不正确（线性）的混合器上得到伽马正确的结果"。做法：按文字颜色每通道亮度选一张 256 项查找表（index = (R >> (8 − kMaxLumBits)) × 256），表的构造：apply_contrast(a, c) = a + (1 − a) × c × a，再在线性光下算 linOut = linSrc × a + linDst × (1 − a)，存入的是让线性混合器复现 linOut 的编码 alpha：result = (out − dst) / (src − dst)。参数：fDeviceGamma（2.6 定点，0 表示 sRGB）、fContrast（0.8 定点）、fLumBits。Chromium 的取值（"近似系统浏览器"）：

4.5 次像素（LCD）渲染

ClearType 管线：光栅器输出过采样位图 → 滤波 → 逐通道 alpha。微软白皮书："标准 ClearType 用 6×1 滤波：x 方向六倍分辨率，y 不变"；对称平滑是 6×5。GDI ClearType 没有亚像素定位。Platt 2000 年论文的滤波器由"受心理物理实验启发的误差度量"（亮度/对色权重）最优化得到，效果"相当于小 25% 字号下的标准抗锯齿"；"位移滤波"是每个通道的滤波器以该子像素的物理位置为中心。微软实际系数未公开。

FreeType 的 FIR 滤波（权重以 1/256 计，作用于 3× 过采样覆盖，须对称、色平衡、归一）：

Harmony（2.8.1，2017，不编译 ClearType 式滤波时的默认）：把轮廓分别平移 −1/3、0、+1/3 像素渲染三次，各取一个通道。"因为平移不改变积分覆盖，所以对彩边免疫"，且 FT_Library_SetLcdGeometry 可给任意三点几何，能适配非条纹布局。

为什么 LCD 文字需要不透明背景（WebRender 文档的公式）：

  • 灰度：result = text × mask.a + (1 − text.a × mask.a) × dest，GL 混合 ONE, ONE_MINUS_SRC_ALPHA。
  • 分量 alpha：对 c ∈ {r,g,b}，result.c = text.c × mask.c + (1 − text.a × mask.c) × dest.c。每个通道的 alpha 不同，不存在单一像素 alpha，因此"只支持不透明目标"。GPU 实现：(1) 混合常量技巧（CONSTANT_COLOR, ONE_MINUS_SRC_COLOR，仅单一文字色）；(2) 两遍（ZERO, ONE_MINUS_SRC_COLOR 再 ONE, ONE）；(3) 双源混合（ARB_blend_func_extended），一遍两输出。

DirectWrite 同样说明 ClearType"对红绿蓝分别计算覆盖……没有单一 alpha，不适合渲染到透明中间位图"；Direct2D 在目标带 alpha、PushLayer 未指定 INITIALIZE_FOR_CLEARTYPE、或 OUTLINE 模式下自动降级为灰度，并建议灰度"质量与 ClearType 相当但快得多"。

DirectWrite 渲染模式：GDI_CLASSIC（水平抗锯齿，整数前进宽，与 GDI 兼容）、GDI_NATURAL（前进宽接近设计值但仍取整）、NATURAL（水平抗锯齿 + 亚像素定位）、NATURAL_SYMMETRIC（x、y 都抗锯齿，"通常用于大字号"）、OUTLINE。Skia 的选择逻辑：gasp 有 SymmetricSmoothing → NATURAL_SYMMETRIC；有 hint、gasp 为空或 v0 且 < 20 像素 → NATURAL（非对称，因为有些字体"依赖 y 方向的丢点控制"）；否则 NATURAL_SYMMETRIC。

被什么杀死：XP 时代的 ClearType 只支持水平 RGB/BGR 条纹，竖屏退化；平板需要旋转，"彩色 ClearType 需要知道背景像素颜色，妨碍平滑滚动与缩放"，UWP 改用灰度。PenTile RGBG 中绿子像素与像素一一对应而红蓝共享，三等条纹假设不成立；2021 年"几乎所有"移动 OLED 是 PenTile 变体。

05算法详解 III：GPU 时代的文字

5.1 字形图集：CPU 光栅化 + GPU 合成

这是 2026 年仍占主流的路径。要点：

  • 打包算法：Skia RectanizerSkyline（"部分基于 Jukka Jylänki 的工作"）维护天际线段 {x, y, width}，为每个矩形扫描能放下的最低左位置，合并层级，percentFull = areaSoFar / (w×h)。WebRender 用 étagère 的货架打包：按相近高度开行，从左到右放，支持 deallocate(id)，"对大量尺寸相近的项（动态字形图集）效果很好"。Android HWUI 旧版 CacheTexture 用列式空闲表：先看能否放进已开的列，否则从剩余空间开新列；A8 与 RGBA（彩色表情）分开；mDirtyRect 只上传脏区。
  • 绘制：每个字形是一个采样图集的纹理四边形（A8、LCD 用 RGB、彩色用预乘 RGBA）。四边形上的 MSAA 没有意义，抗锯齿已在纹理里。图集须留 ≥ 1 纹素透明边，预乘彩色字形的边必须是预乘零而非 (1,1,1,0)，否则出彩边。
  • 代价：每 (字体, 尺寸, 变换, 亚像素偏移, 颜色亮度, 变量轴) 一份；旋转缩放时模糊；图集抖动。Direct2D 建议复用 IDWriteTextLayout，小图打进带透明边的图集。

5.2 Loop–Blinn（2005）：隐式曲线着色器

  • 二次曲线：以三个控制点为三角形，纹理坐标 (0,0)、(1/2,0)、(1,1)，像素在曲线内当且仅当 f(u,v) = u² − v < 0。
  • 三次曲线：隐式函数 f = k³ − l×m（k、l、m 为线性泛函），按拐点多项式判别式分类：蛇形（> 0）、环形（< 0，需分割）、尖点（= 0）、退化二次、直线、点。
  • 抗锯齿：屏幕空间有符号距离 d ≈ f / |∇f|，梯度用 ddx/ddy 与链式法则，alpha = clamp(0.5 − d, 0, 1)。
  • 弱点（Slug 论文的批评）：三角形数与控制点数绑定，小字号下三角形过小，GPU 占用率低。

5.3 有符号距离场（Valve，2007）

  • 生成：高分辨率二值图（如 4096²）→ 每个输出纹素在局部邻域暴力搜索最近的异态纹素 → 用"扩展系数"把有符号距离映射到 [0,1]，8 位存储，0.5 为边 → 输出如 64×64。更快的生成：8SSEDT 两遍 8 邻域扫描；跳跃泛洪（Rong & Tan，I3D 2006）：步长 N/2、N/4…1 各一遍，每像素查 8 个偏移 k 的邻居保留最近种子，约 9 log₂N 次操作/像素，近似解。
  • 渲染：固定管线用 0.5 alpha 测试；着色器 alpha = smoothstep(d_min, d_max, d)，宽度取 fwidth；描边 = 两个阈值之间重新着色；发光 = 0–0.5 段的 smoothstep；投影 = 偏移 UV 二次采样；尖角 = 两个通道的距离场取交。
  • 局限：尖角被圆化；小字号质量差；缩小时距离场采样不足。

5.4 多通道距离场 MSDF（Chlumský，2015）

  • 边着色：给每条边分配 {R,G,B} 的子集（通常各两个通道，即品红/黄/青），使在拐角相遇的边至少有一个通道不同（edgeColoringSimple / InkTrap / ByDistance 启发式）。
  • 每纹素每通道存到该颜色边的有符号距离；重建 median(r,g,b) = max(min(r,g), min(max(r,g),b)) 恢复尖角。管线：加载形状 → 归一化 → 边着色 → 生成 → 误差修正 → 输出。
  • MTSDF：RGB 为 MSDF，A 为真 SDF，供发光/软阴影。着色器：screenPxRange = max(0.5 × dot(pxRange/textureSize, 1/length(dFdx, dFdy)), 1)，opacity = clamp(screenPxRange × (sd − 0.5) + 0.5, 0, 1)。
  • Lengyel 的评价：需要复杂的分析步骤，复杂字形有难以避免的新伪影。

5.5 Slug（Lengyel，JCGT 2017）：直接从轮廓算覆盖

  • 数据：二次贝塞尔 C(t) = (1−t)²p₁ + 2t(1−t)p₂ + t²p₃ 存在 4×16 位浮点纹理（p₁、p₂ 一个纹素，p₃ 与下一条共享），另有 16 位整数"带"纹理。
  • 带：字形按等宽切成水平带与垂直带，数量与曲线数成比例，每方向最多 16；每带内曲线按最大 x（或 y）降序排列；像素沿 +x 射线（垂直带沿 +y），当 max{x₁,x₂,x₃} × m < −1/2 时提前退出。可选在中位数处把带一分为二让远侧像素发负向射线，小字号时因分支发散关闭。
  • 求根与环绕：a = y₁ − 2y₂ + y₃，b = y₁ − y₂，c = y₁，t₁,₂ = (b ∓ √(b² − ac)) / a（a ≈ 0 时 t = c/2b），b² − ac 钳到 ≥ 0 让相切情形抵消。
  • 根分类查表：code = (y₁>0 ? 2:0) + (y₂>0 ? 4:0) + (y₃>0 ? 8:0)，把常量 0x2E74 右移 code 位：位 0 置位则在 t₁ 处若 C_x(t₁) ≥ 0 加 1，位 1 置位则在 t₂ 处若 C_x(t₂) ≥ 0 减 1。这用 3 位符号分类替代了 Dobbie/GLyphy 方案中对 t 的范围测试，消除"闪烁"伪影。
  • 覆盖：f = sat(m × C_x(tᵢ) + 1/2)（m = 每 em 像素数），沿射线加减得到解析抗锯齿；x、y 两条射线结果取平均；可选超采样（射线起点在像素内偏移，"a、b 不变"故可共享计算）。几何体是切角包围四边形（≤ 8 边形）。
  • 性能（GTX 1060，200 万像素、32 ppem）：Arial 1.1 ms（图集采样 26 µs）、Centaur 1.3 ms、Wildwood 13.3 ms；Dobbie 约慢 4 倍；预处理数据是 TTF 的 2 至数倍（Arial 894 KB → 1549 KB）。支持 COLR/CPAL 分层。

5.6 矢量纹理与三角扇（2016）

Will Dobbie：字形按网格分格，每格存相交二次曲线索引于"矢量图集"纹理；每像素水平射线，进入时累加（窗口右边 − 交点），退出时减去，得一维覆盖；四个角度的射线用抛物线窗平均。Evan Wallace：从任意点出发的三角扇配奇偶翻转混合得多边形内部，Loop–Blinn 三角形补曲线部分，多次抖动偏移累加做抗锯齿。

5.7 计算着色器：Pathfinder 与 Vello

  • Pathfinder v1（Walton，2017 年 2 月）：贝塞尔在 GPU 上剖分为小线段 → 扩成屏幕对齐四边形 → 片段着色器把覆盖差分（相对上方像素的梯形面积）加法混合写入浮点帧缓冲 → 计算着色器做列前缀和。这就是 font-rs 的累加搬到 GPU。
  • Pathfinder v3（2019）：CPU 把路径切成 16×16 瓦片，分为纯色瓦片与蒙版瓦片并跟踪瓦片边界环绕数；蒙版瓦片里每条边作为"下边吸到瓦片底"的四边形提交，片段写 0/±1/分数面积，加法混合进浮点蒙版纹理；纯色瓦片实例化绘制；被不透明瓦片遮挡的瓦片剔除。相当于 256× 抗锯齿。
  • Vello 计算渲染器（2020–）：场景编码 → 计算着色器展平曲线 → 分箱 → 粗光栅（每瓦片命令列表）→ 精光栅（每瓦片精确面积覆盖）。2026 年退为实验分支，主力转向 4.3 节的 Sparse Strips CPU/GPU 混合，并新增 glifo 字形与涂料 crate。

5.9 彩色字形、变量字体与整形缓存

  • 位图彩色：sbix 按 ppem/ppi 存 PNG/JPEG/TIFF 条带，缺尺寸时"选最近的更大尺寸或整数倍尺寸"缩放，缩小即模糊；CBDT/CBLC 类似。Noto Emoji 位图 9 MB，COLRv1 版 1.85 MB WOFF2。
  • COLRv0：Z 序图层，每层普通轮廓填 CPAL 颜色（0xFFFF = 前景色）。COLRv1：绘制有向无环图，节点含纯色、线性/径向/扫掠渐变、变换、合成模式、PaintGlyph、嵌套 PaintColrGlyph、形状复用、原生变量；FreeType 只暴露图（FT_Get_Color_Glyph_Paint），"需要 Skia 或 Cairo 这类图形库来执行绘制命令"。图集必须存预乘 RGBA 而非 A8，且禁用 LCD。
  • 变量字体实例化：每字形对每个适用区域算标量（归一化 2.14 轴坐标）、解压游程编码的点号与增量、point += Σ scalar_i × delta_i、对未引用点做 IUP 式插值；复合字形先变分量偏移再对每个分量跑 hinting，cvar 变 CVT；度量应取 HVAR 以免跑光栅器。每个轴元组是一个新 strike，缓存项成倍增加；ttfautohint 不支持变量字体。
  • 整形缓存：HarfBuzz 只缓存整形计划（hb_shape_plan_create_cached，按 face + 段属性 + 用户特性），不缓存整形结果；词级缓存在客户端：Blink ShapeCache（按字体、短字符串键）、Minikin LayoutCache（LRU，键为文本 + 画笔 + 字体集 + 方向）。Behdad：因字形与字体缓存，光栅化"通常只占实际渲染时间的一小部分"。

Windows 现代（DirectWrite/D2D/UWP）只垂直DirectWrite灰度对称（推荐）/ ClearType 仅不透明Direct2D 图集 + 像素着色器
macOS / iOS忽略Core Graphics，覆盖伽马 2.0 + 膨胀灰度，亚像素定位Core Animation 图集
Linux 桌面FreeType v40（只垂直）或自动 hinter lightftgrays 精确面积灰度或 Harmony/FIR LCD合成器 GPU；缺线性混合
AndroidSkia kSlight → FreeType lightFreeType（Skrifa 在 Chrome 中）灰度，预混伽马 1.4HWUI/Skia 图集，Vulkan
Chrome（全平台）随平台Skrifa（Rust，Chrome 145 起无 FreeType）灰度，SkMaskGamma 预混Skia Ganesh/Graphite 图集，大字号 SDF
Firefox随平台平台 API → CPU灰度；LCD 仅不透明层（双源混合）WebRender 图集，étagère 货架打包
游戏无预计算 SDF/MSDF 或 Slug 运行时着色器 smoothstep / 解析覆盖纹理四边形
新框架（Linebender、Bevy）无Vello Sparse Strips（CPU 或 CPU+GPU）精确面积条带上传 GPU

整体判断：hinting 已从"必需"退为"垂直吸附可选"，彩色次像素渲染在移动端从未存在、在桌面正在退场，精确面积覆盖光栅化是所有 CPU 与混合方案的共同内核，GPU 直接从轮廓算覆盖的方案（Slug、Vello）在游戏与新框架中站稳但尚未进入浏览器与系统 UI。移动端不是 PC 的缩小版，而是先一步走完了"忠实轮廓 + 灰度 + GPU 合成"的路线，PC 在 HiDPI 之后正在向它靠拢。
