00总览

0.1 一句话结论

2D 管线的内容在四十年里换了一次"物理"：从整数像素上的布尔运算（BitBLT、光栅运算）变成带覆盖率与 alpha 的路径合成（PostScript 模型）。专用 2D 引擎擅长前者，不擅长后者；等到 GPU 把三角形光栅化、纹理采样和可编程混合做得足够便宜，2D 的每一种操作都在 3D 管线上找到了更快的等价物，专用 2D 引擎便被冻结或删除。字体是这条路上最难的一段：轮廓字体光栅化对小尺寸的像素级要求，使它成为最后一个完全迁移到 GPU 的 2D 操作，而高分屏的普及反过来削弱了 hinting 与次像素渲染存在的理由。

012D 渲染管线包含什么

1.1 阶段划分

2D 管线没有 3D 那样公认的"标准图"，但从 QuickDraw 到 Skia，所有实现都可以拆成下面这些阶段：

绘图命令(原语 + 属性)
  → 几何: 点、线、矩形、多边形、椭圆、贝塞尔路径、文字(字形轮廓)
  → 变换: 平移/缩放/旋转/斜切 (2×3 仿射矩阵)
  → 裁剪: 矩形 → 区域(Region/HRGN) → 任意路径与蒙版
  → 光栅化(扫描转换): 把几何变成像素集合或逐像素覆盖率
  → 抗锯齿: 覆盖率(精确面积或超采样)
  → 着色: 纯色、图案、渐变、图像纹理
  → 合成: 光栅运算(ROP) 或 Porter–Duff alpha 混合
  → 帧缓冲: 脏矩形、双缓冲、翻页 → 窗口合成 → 显示

关键在于"光栅化 + 合成"这两段的语义变化：早期系统把像素看作整数位，用布尔运算搬运；PostScript 之后把像素看作被路径部分覆盖的面积，用 alpha 混合。这个语义变化决定了硬件的命运。

1.3 BitBLT：2D 管线的第一原语

BitBLT（bit block transfer，维基百科另给出 bit-boundary block transfer 的展开）于 1975 年 11 月在 Xerox PARC 由 Dan Ingalls、Larry Tesler、Bob Sproull、Diana Merry 为 Alto 上的 Smalltalk-72 编写，随后 Ingalls 用 Alto 微码重写。Alto（1973 年 3 月）"把位块传送操作确立为显示器的基本编程接口"。一次 BitBLT 定义为：源矩形、目标矩形、可选的半色调图案、裁剪矩形，以及一个组合函数（拷贝、与、或、异或等）。文字、光标、窗口移动、滚动、画线都归结为 BitBLT。Ingalls 在 1981 年 8 月的 Byte 杂志《The Smalltalk Graphics Kernel》中公开描述了它。

这套"整数像素 + 布尔组合"模型直接被 QuickDraw（CopyBits）、GDI（BitBlt）和 X11（XCopyArea）继承，也直接定义了 1987–1996 年 2D 加速引擎的指令集。

1.4 成像模型的两个家族

家族代表像素语义曲线抗锯齿透明
位块/光栅运算模型Alto、QuickDraw（1983/84）、GDI（1985）、X11 核心协议（1987）整数位或调色板索引无（QuickDraw 只有直线、矩形、椭圆、多边形；GDI 在 NT 加了贝塞尔）无只有掩码/色键
路径/合成模型PostScript（1984）、NeWS（1986）、Display PostScript（1987）、Java 2D（1998）、XRender（2000）、GDI+（2001）、Quartz 2D（2001）、Cairo（2003）、Skia（2004）、Direct2D（2009）浮点坐标下的覆盖率与 alpha三次贝塞尔（PostScript/Quartz/Cairo）或二次（QuickDraw GX）覆盖率抗锯齿Porter–Duff

演进顺序：

  • PostScript（1984）。Warnock 与 Geschke 的 Adobe 于 1982 年 12 月成立，PostScript 把一切（包括文字）表示为直线与三次贝塞尔组成的路径，用"模板/涂抹"模型填充，非零环绕规则，设备无关。它先服务打印机（LaserWriter 1985），随后 NeWS（Sun，1986）和 Display PostScript（NeXT 1987 年授权，1988 年随 NeXT 出货）把它搬到屏幕。
  • QuickDraw（1983/84）。源自 Lisa 的 LisaGraf，Atkinson 与 Hertzfeld 编写，纯光栅、区域裁剪、无贝塞尔。QuickDraw GX（1994）引入二次贝塞尔、3×3 变换与定点分数坐标，但随 Mac OS 8 被放弃。
  • X11（1987）→ XRender（2000）。核心协议没有抗锯齿和透明；Keith Packard 的 XRender 扩展（XFree86 4.0.1）加入 Porter–Duff 合成、服务器端字形和由客户端三角化后的梯形几何，动机正是核心协议"无法在不做读-改-写的情况下画透明或抗锯齿对象"。
  • GDI（1985）→ GDI+（2001）。GDI+ 随 Windows XP 加入抗锯齿、浮点坐标、渐变、alpha 与 PNG/JPEG，但完全软件渲染。Direct2D（2009）是其继任者。
  • Quartz 2D（2001）。1999 年 WWDC 以 Core Graphics Rendering 之名展示，Mac OS X 10.0 出货，绘图模型基于 PDF 1.4，部分原因是避免 Display PostScript 授权费。
  • Cairo（2003）、AGG（Maxim Shemanarev，2.5.0 为 2006 年）、Skia（Skia Inc. 2004 年成立于北卡，Google 2005 年收购，2008 年开源，Android/Chrome/Flutter 使用）是这一模型的三个通用开源实现。

1.5 抗锯齿路径光栅化的两种思路

思路做法代表
超采样每像素 N×N 子采样点，数落在路径内的个数Skia 早期 16× 超采样（SkScan_AntiPath.cpp，2006）
精确面积累加把路径每条边对每个像素单元贡献的有符号面积与覆盖累加，再按扫描线做前缀和得到环绕数与覆盖率libart（Raph Levien）→ FreeType "smooth" 光栅器（David Turner，2000，头注明"基于 Raph Levien 的 LibArt"）→ AGG → font-rs（Levien，稠密累加缓冲 + SIMD）→ Vello Sparse Strips

精确面积法的问题是"合并伪影"（conflation artifact）：相邻两个形状的覆盖率各为 50%，合成后不是 100% 而是 75%，出现接缝。这在 GPU 路径渲染器（Vello、Pathfinder）的设计讨论中反复出现。

1.6 从画家算法到合成

传统窗口系统（X11、Win9x GDI、经典 Mac）是单一帧缓冲 + 裁剪区域 + 画家顺序：每个窗口直接往帧缓冲里画，被遮挡的部分靠裁剪区域剔除，露出时要重画。合成式窗口系统给每个窗口一块离屏后备存储，最后由合成器按顺序叠加。一旦这样做，"最后一步"就精确等于 GPU 的本职：把每块后备存储当纹理，每个窗口画一个带纹理的四边形，混合、缩放、旋转、特效全部并行完成，损坏跟踪退化为重传脏矩形。这是 2D 迁往 3D 管线的第一道门。

022D 硬件加速的演变：从专用引擎到 3D 管线

2.1 第一阶段：固定功能 2D 引擎（1987–1996）

前一份报告《从帧缓冲到 GPU》已详述这一段，这里只列结论。IBM 8514/A（1987）是 PC 上第一块命令式绘图协处理器：BitBLT、Bresenham 画线、区域填充、单色到彩色扩展（文字）、剪裁矩形、光栅运算。S3 86C911（1991 年 6 月）把同样的操作集做进单芯片并卖给大众市场，"Windows 加速器"随之成为品类。TI TMS34010（1986）走了另一条路：一颗带 PIXBLT 指令的 32 位 CPU，一切都是软件，但成本过高。

这一代硬件加速的对象与 GDI 驱动接口一一对应：BitBlt、PatBlt、ExtTextOut（颜色扩展）、Output（线/多边形）、光标、后来的视频覆盖层与缩放。X11 方面，XFree86 的 XAA（Harm Hanemaayer，1996，XFree86 3.3）把同样的操作抽象成驱动钩子。

2.2 第二阶段：语义错位（1998–2008）

问题在 1.4 节已经埋下：新的成像模型要的是抗锯齿、alpha 混合、任意路径、渐变，而 2D 引擎只会整数矩形上的布尔运算。结果是加速反而退化：

  • XRender（2000）与 EXA（2005）。XRender 的合成操作在大多数 2D 引擎上没有对应指令，XAA 只能把它交回 CPU。Zack Rusin 在 LinuxTag 2005 发布的 EXA（源自 kdrive 的 KAA）以"正确加速 XRender"为目标重新设计驱动架构，但底层硬件的 2D 引擎仍是瓶颈。
  • Windows Vista WDDM 1.0（2006）。GDI/GDI+ 在 Vista 上继续用软件渲染，画到系统内存表面，DWM 再把这些表面作为纹理合成。这意味着 Vista 的 GDI 反而比 XP 慢，DWM 还要为每个 GDI 表面保留一份系统内存副本。
  • Windows 7 WDDM 1.1（2009）。恢复了一小组 GDI 操作的硬件加速：BitBlt、ColorFill、AlphaBlend、StretchBlt、TransparentBlt、ClearTypeBlend，并把它们定义成内核驱动接口（DXGK_GDIARG_*）。注意这份清单：没有画线，没有多边形，没有路径；有的全是矩形与混合。它实际上是在 3D 引擎上实现的"矩形 + 混合"子集，GDI+ 完全不在其列。

2.5 厂商删除或冻结 2D 引擎

  • AMD/ATI：R600 / Radeon HD 2000（2007 年 5–6 月）起开源驱动的 EXA 路径用 3D 引擎与着色器实现 2D（r600_exa.c），X.Org 特性表从 Evergreen 起只列 Glamor。AMD 驱动开发者多次说明 R600 之后没有专用 2D 引擎，这一表述广为引用但本次未取得可直接引用的原文。
  • NVIDIA：公开类文档显示 2D 对象类逐代演进（NV1/NV3 的 ROP、CLIP、PATTERN、BLIT，G80 的统一 2D 类 0x502D），到 Fermi 的 0x902D（2010）之后再无新版本，此后所有世代继续暴露这同一个类；相比之下拷贝引擎类每代都更新（cl85b5 到 clcab5 共 13 版）。0x902D 仍定义 RenderSolidPrim（点/线/三角形/矩形）、PixelsFromMemory 缩放位块、SetRop、SetPatternSelect、SetClip、SetColorKey，即 1991 年 Windows 加速器的全部指令集。它在新芯片上是专用硅片还是内部由 3D 管线模拟，未见公开资料。
  • Intel：Xe 架构仍有拷贝/位块引擎（BCS），但用于内存搬运与清除（XY_BLOCK_COPY_BLT、XY_FAST_COLOR_BLT），不再用于绘图。
  • 仍然保留的固定功能：拷贝/DMA 引擎；显示平面（Linux KMS 的 PRIMARY/CURSOR/OVERLAY 平面、Windows MPO、Android HWC 覆盖层）与硬件光标。它们存在的理由恰恰是避免一次 GPU 渲染：视频与光标由显示引擎在扫描输出时混合，功耗最低。

一个常被忽略的事实：TrueType 光栅化在小尺寸下的目标恰恰是模拟手工点阵字体的效果。TrueType 规范以 9 磅 Arial 的 "m" 为例说明字干与像素网格的相位偶然性会让笔画消失，grid fitting 的目标是字干粗细一致、颜色（灰度密度）均匀、间距一致、不丢点，并建议屏幕字体在 9 ppem 仍可读。

3.4 轮廓字体的光栅化算法

流程（按 TrueType 规范，对其他格式同样适用）：

FUnit 轮廓 → 缩放到设备像素: ppem = 磅值 × dpi / 72，26.6 定点
  → grid fitting (hinting): 移动控制点使字干/对齐区落到像素边界
  → 贝塞尔展平: 递归细分为线段
  → 扫描转换: 像素中心在轮廓内(非零环绕)则点亮
  → 丢点控制 (dropout control): 相邻像素中心之间同时出现进出交叉时补点，排除"残桩"
  → 位图 / 覆盖率图

为什么要 hinting。ppem 小于约 20 时，一条 1.3 像素宽的字干可能落成 1 像素或 2 像素，甚至因为两条边落在同一像素内而消失。hinting 把轮廓"捏"到网格上：字干统一为整数宽度，x 高度与基线对齐到像素行，过冲（overshoot）在小尺寸被压平。

两种 hinting 哲学：

  • Adobe（Type 1 / CFF）：字体只声明"这里是一条竖干、这些是对齐区"，光栅器自带算法做字干吸附与对齐区处理。字体制作便宜，效果取决于光栅器。
  • TrueType：字体携带完整程序，光栅器只是一台虚拟机。效果可以精确到"在 11 ppem 把这个点向上移 1/64 像素"，因此微软核心字体（Verdana、Georgia，1996，Matthew Carter 设计）在 Windows 上的小字号效果无人能及，但制作极其昂贵，且严重依赖特定光栅器的行为。

FreeType（David Turner 1995 年为 OS/2 开始，Pascal 编写，1997 年 Robert Wilhelm 移植到 C；2.0 于 2000 年模块化重写）是自由软件世界的光栅器。1999 年 Apple 提出专利问题后，字节码解释器默认关闭，发行版只能用 自动 hinter（分析轮廓并做轻度垂直吸附）；专利 2010 年 5 月到期，2.4.0（2010 年 7 月 12 日）默认开启字节码解释器。它的 "smooth" 光栅器输出覆盖率位图，用 1.5 节的精确面积累加法。Keith Packard 的 Xft 与 fontconfig 让 FreeType 的抗锯齿字形经 XRender 进入 X11。

3.6 布局与整形栈

字体渲染管线不只是光栅化。完整的文字栈是：字体加载与回退 → 整形（shaping：把字符序列按 GSUB/GPOS 变成字形序列与位置）→ 行布局 → 字形光栅化 → 合成。整形层的演变：Uniscribe（Windows 98 SE / 2000 / IE5）、ATSUI（Mac OS 8.5，1998）→ Core Text（10.5，2007）、Pango（Owen Taylor，2000 年命名，1.0 于 2002）、HarfBuzz（源于 FreeType 的 OpenType Layout 代码，2006 年独立，Behdad Esfahbod 2010–2012 年重写为 HarfBuzz NG，2013 年进入 Android，1.0 于 2015）。DirectWrite（2009）引入亚像素定位（字形可从任意亚像素位置起笔）与大字号的 y 方向抗锯齿，并把 ClearType 混合放到 GPU 上（Direct2D 的 DrawGlyphRun 硬件加速"从合并字形到应用 ClearType 混合算法的全部阶段"）。

浏览器的现实选择很保守：Chrome 的 Skia 在 src/text/gpu/ 里是 StrikeCache 图集加 SDF 用于大字号或变换文字；Firefox WebRender 的字形由平台 API（CoreText/FreeType/DirectWrite）在 CPU 光栅化后缓存到 GPU 纹理，次像素抗锯齿仅在不透明目标上启用（用双源混合或双通道实现）。也就是说，2026 年主流文字渲染仍是"CPU 光栅化 + GPU 合成"，Slug/Vello 一类纯 GPU 方案主要在游戏与新框架中。

3.8 高分屏的反作用：去 hinting、去次像素（2010–2018）

  • Retina 于 2010 年（iPhone 4）与 2012 年（MacBook Pro）到来后，200+ ppi 让 1 像素的相位误差不再可见。macOS Mojave（2018 年 9 月 24 日）移除次像素文字渲染；Quartz 此前已基本忽略 hint。
  • 微软从 Windows 8 起在文档中明确"多数情况下应使用灰度抗锯齿"，UWP/XAML 用灰度，因为"质量与 ClearType 相当但快得多"，也因为 ClearType 无法用于透明合成层。
  • FreeType 2.7（2016 年 9 月）把 v40 TrueType 解释器设为默认：忽略所有水平方向 hint 指令，只保留垂直对齐，得到 ClearType/DirectWrite 风格输出；v40 是 Infinality 补丁（v38）的精简版。
  • 词干加深（stem darkening）在 Adobe CFF 引擎（2013）实现，但因 X11 栈缺少线性空间混合与伽马校正而默认关闭。

结论：hinting 与次像素渲染是低分辨率时代的补偿技术；分辨率上去之后，行业回到"忠实渲染轮廓 + 灰度覆盖率"，这反而让 GPU 方案（不需要 hint VM、不需要 RGB 滤波）更容易落地。

3.10 2024–2026：Rust 字体栈与 GPU 渲染器的现状

  • Chrome 用 Skrifa 替换 FreeType（Google fontations 项目，Rust）：Chrome 128（2024 年 8 月）彩色字体与 CFF2，Chrome 133（2025 年 2 月）Linux/Android/ChromeOS 全部 Web 字体，Chrome 136 系统字体，Chrome 145 从 Blink 中完全移除 FreeType。理由是内存安全，Google 估计 FreeType 的安全维护占至少 0.25 全职人力。
  • HarfRust：HarfBuzz 组织下的 Rust 移植，基于 read-fonts，跟踪 HarfBuzz 14.3.1；HarfBuzz 本身 14.4.0（2026 年 8 月）。
  • Linebender 栈：Parley（富文本布局）依赖 Fontique（枚举/回退）、HarfRust（整形）、Skrifa（轮廓）、ICU4X；Bevy 的 bevy_text 已改用 Parley。Vello 0.7.0（2026 年 1 月）→ 0.10.0（8 月），Sparse Strips 0.1/0.2（7–8 月）。
  • Skia Graphite 2025 年 7 月在 Chrome M134 上线，但公告未提及文字渲染的改变。
  • 游戏：Slug 授权给 ZeniMax Online、Blizzard、Quantic Dream、Fatshark 等；Unity TextMeshPro 推荐 SDF 图集作为默认字体资产类型。

三条线在 2026 年汇合成一个事实：除了扫描输出时的显示平面混合，2D 已没有专用硬件；一切绘图都是三角形、纹理与着色器，2D API（Direct2D、Skia、Core Graphics、Vello）只是 3D API 上的一层软件。字体是这层软件里最后仍主要依赖 CPU 光栅化的部分，原因不在硬件，而在小字号下像素级质量与 hinting、次像素渲染这些"历史包袱"，而高分屏正在慢慢卸下这些包袱。
